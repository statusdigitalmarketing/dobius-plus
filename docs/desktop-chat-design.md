# Desktop Chat view for Dobius+ project windows: design for review

## Ask (Sam, verbatim intent)
In the project window header (TopBar, next to Visual / Tasks / Speak) add a button to switch the active tab between the raw terminal and a CHAT view, "like we have on mobile but for desktop", so non-technical teammates (Bryan) can read and interact easily. Over time the desktop chat should become "clean, enhanced, high-level and work just as well as a Claude desktop application", still driving the same Claude Code session in the same PTY.

## What exists
- Mobile PWA chat: mobile/ChatView.jsx (642 lines). Talks to the Mac over WS via a `connection` object (send/onMessage/token). Uses only these message types: loadTranscript (poll every 3.5s, sig-based "unchanged" replies), selectorSnapshot (parses Claude's live numbered menus out of the PTY so they render as buttons), terminalText (plain tail for sessionless tabs), submitPrompt (bracketed paste then a discrete Enter 250ms later), input (raw keys: Esc, arrows, option digits), listSkills (slash-command catalog). Uploads go through fetch(absUrl('/upload')). Styled by mobile/styles.css (has globals: :root, *, html, body).
- Server side for those: the WS switch in electron/mobile-server.js:639-960 (per-socket _authedTabs, MAX_INPUT_BYTES, invalidateSelectorPush, liveSelectorForTab, stripAnsi+getTerminalBuffer, getTranscriptSig + per-socket tx cache, data-service loadTranscript returning {role, content} text entries with tool_use/tool_result/thinking stripped).
- Desktop: TopBar.jsx (Visual button, TasksDropdown, SpeakButton), ProjectView.jsx owns tabs (Zustand store.js terminalTabs, activeTabId), TerminalPane per tab and ALL tabs stay mounted with display:none (unmounting kills the xterm buffer + PTY). Which session a tab runs is main's call: ipc tabs:liveSessions (tab-context.js resolveSessionForTab). PTY ownership per window: terminalOwners / getTerminalWebContentsId(id).

## Proposed design (phase 1)
1. electron/chat-service.js: extract the six handlers' logic from mobile-server.js into transport-neutral async functions (transcriptFor({sessionId, projectPath, limit, sig, cache}), selectorFor(tabId), terminalTextFor(tabId), submitPrompt(tabId, text), sendInput(tabId, data), listSkills()). mobile-server.js WS switch calls them (behaviour unchanged).
2. IPC chat:* handlers in main for the desktop, each REQUIRING the calling window to own the tab (getTerminalWebContentsId(tabId) === event.sender.id) for anything that writes to or reads a PTY, and the session to be the one main resolves for that tab for transcript reads.
3. Renderer adapter src/lib/desktop-chat-connection.js: same interface as mobile Connection (send(msg), onMessage(cb), token=null, status), mapping send() to ipcRenderer.invoke and emitting the reply as the same {type: 'transcript'|'selector'|'terminalText'|'skills'} messages, so mobile/ChatView.jsx runs unmodified except an optional `connection.upload(file)` hook (desktop: no upload server; return the dropped file's local path directly).
4. Reuse mobile/ChatView.jsx in the desktop renderer, imported from src via ../../../mobile/ChatView.jsx, with a desktop stylesheet scoped under `.dchat` re-skinning its class names with the desktop CSS vars/theme; do NOT import mobile/styles.css (globals).
5. Store: per-tab `viewMode: 'terminal' | 'chat'`, persisted with the tab (config.projects[path].tabs). TerminalPane stays mounted underneath (display:none or visibility) when in chat; switching back shows the live xterm untouched. Chat view only for kind 'terminal' tabs.
6. TopBar: a "Chat" / "Terminal" segmented toggle beside Visual, acting on the active tab; shortcut Cmd+Shift+C (verify free). Tear-off windows get it too.

## Phase 2 (not in this branch)
Claude-desktop-grade rendering: tool calls as collapsed rows (Read X, Ran `cmd`, Edited Y with diff), thinking collapsed, running status/spinner from the tab's hook status, permission prompts and AskUserQuestion menus as proper cards, image paste, @-file mention, model/effort picker. Needs data-service to stop stripping tool_use/tool_result and emit typed blocks (affects mobile payload size; versioned field).

## Questions for the reviewer
- Is reusing mobile/ChatView.jsx (shared component, two skins) right, versus a desktop-specific component that shares a hook (useChatSession) for polling/selector/submit logic? Phase 2 will push desktop far richer than mobile.
- Authorization model for chat:* IPC: is window-owns-tab sufficient? Tear-off/dock moves ownership mid-session.
- Polling 3.5s transcript + 2.5s selector per visible chat in-process: any main-thread cost concern given the stall watchdog history? Only the ACTIVE tab's chat should poll.
- Anything in the six handlers that silently depends on WS/socket state (per-socket cache, _authedTabs, noteSelectorInterest push pipeline) that would break or leak when called from IPC.

## Codex design review (2026-10-27), verbatim

I would revise the plan before implementation. Static review only.

1. **Component reuse:** Prefer a desktop component sharing `useChatSession` and small rendering components. `ChatView` mixes transport, uploads, drafts, polling, and mobile controls. Two skins alone will not accommodate phase 2 cleanly.

2. **Authorization:** Window ownership is the right starting boundary, but a check at handler entry is insufficient. Validate ownership and PTY generation across asynchronous work, delayed writes, and pushes. Resolve the complete session/project tuple in main.

3. **Polling:** There is a real main-thread cost concern. Transcript parsing can process an 8 MB tail; selector probes replay 262,144 characters through one serialized headless xterm. Keep the intervals initially, with visibility gating, one outstanding request per operation, and shared work across consumers.

4. **Socket dependencies:** Yes. Preserve `_authedTabs`, reconnect ordering, per-consumer transcript signatures, selector interest/deduplication, and delayed selector refreshes explicitly. Keep WS authorization in its adapter; make shared selector subscriptions independent of mobile-server startup/shutdown.

## Revised phase 1 plan (after review)
- `useChatSession(tabId)` hook shared by mobile ChatView and a new desktop `ChatPane`: polling, sig cache, request ordering by tab + session generation, echoes, selector state. Mobile keeps its UI.
- Main: `electron/chat-service.js` with transport-neutral ops (keeps `source` and the no-limit History path), a per-tab serialized paste+Enter transaction shared by WS and IPC, ownership + PTY-instance rechecks before every deferred write and reply, cancelAutoResumeTab on accepted chat input, selector subscriptions that live independently of the mobile server.
- IPC `chat:context` (owned tab -> {sessionId, projectPath, claudeLive, status}, covering idle/unresolved/exited), `chat:transcript`, `chat:selector`, `chat:terminalText`, `chat:submit`, `chat:input`, named in preload; correlated success/error so a failed send keeps the draft.
- Desktop ChatPane: desktop-themed, anchors open via the validated openExternal bridge, files via getPathForFile / saveClipboardImage with consistent quoting, polls only when it is the active tab in chat mode and visible.
- TerminalPane: paste/drop/Cmd+F/focus handlers gated on being the active terminal SURFACE (not just the active tab); stays mounted.
- Store: per-tab `viewMode`, carried through every serializer (primary, extra windows, tear-offs, dock, reopen); missing means terminal.
- TopBar: Terminal / Chat toggle beside Visual for the active tab; Cmd+Shift+C (free).
